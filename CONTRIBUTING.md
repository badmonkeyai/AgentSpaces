# Contributing to AgentSpaces

Thank you for your interest in contributing. AgentSpaces is an Apache 2.0 project
from Bad Monkey, Inc., and everything in this repository stays Apache 2.0 —
features may be added to the open core over time, and nothing ever moves from
open to paid. 

There are plenty of customization points in AgentSpaces, from building your own peers - even AssetCard only peers into other products, SPI for security (e.g. a keycloak authorizer SPI). These are great ideas for a standalone project, whether they be open or closed. We'd like to keep this repository focused on the core layers and services offered.

## Before you start

- **Questions and ideas** are welcome as [GitHub issues](https://github.com/badmonkeyai/agentspaces/issues)
  or discussions. For anything protocol-shaped, read `SPEC.md` and
  `TECH-SPEC.md` in `agentspaces-spec/` (beside this repository) first — the wire format, algorithms, and their rationale
  are specified there, and design conversations go faster against the spec.
- **Security issues** must not be filed as public issues. See
  [SECURITY.md](SECURITY.md) for private reporting.
- **Code of conduct:** by participating you agree to the
  [Code of Conduct](CODE_OF_CONDUCT.md).

## Building

The build needs JDK 21 and Maven. On a normal network:

```
mvn verify
```

resolves everything from Maven Central. Two opt-in profiles matter:

- `-Pspring-it` adds the real-Spring integration test (activated automatically
  in CI); it must be green before any release.
- `-Pperf` adds the JMH benchmark and stress-harness module.

Network-restricted environments (sandboxes that block Maven Central) are
first-class: see `docs/BUILD-ENVIRONMENTS.md` for building against the
Debian/Ubuntu system Maven repository.

Run module builds from the repository root (`mvn -pl <module> ...`), never from
the module directory.

## Developer Certificate of Origin (DCO)

Contributions require a [DCO](https://developercertificate.org/) sign-off:
every commit must carry a `Signed-off-by` line matching the commit author,
which `git commit -s` adds for you. Signing off certifies that you wrote the
change or otherwise have the right to submit it under the Apache 2.0 license.
A bot will check this on pull requests.

## Pull requests

- Keep PRs focused; separate refactoring from behavior changes.
- Every source file carries the Apache 2.0 header — the build enforces it.
- Public classes and methods carry javadoc; packages carry `package-info.java`
  stating their role and stability level (`API`, `SPI`, or `internal`).
- Tests accompany changes. The framework modules carry per-module JaCoCo
  line-coverage gates that CI enforces; deterministic tests use
  `agentspaces-test-support` (`SimNetwork`, `TestClock`) rather than sleeps.
- Prefer allocation-conscious code on hot paths (gossip fan-out, template
  matching, CRDT merge); reflection is reserved for startup-time binding.

### Submit a pull request

Should you create an issue first?
No, just create the pull request and use the description to provide context and motivation, as you would for an issue.
You only have to create an issue if you want to start a discussion first.

Please don't submit pull requests:

* With GitHub accounts managed by autonomous AI bots
* For already assigned issues (as the assignee is or plans to work on it)
* For straightforward or polish-style changes, feel free to create a ticket on those or send a note to 'oss@badmonkey.ai' if you've found polish issues you are passionate about.

The pull request title is used to generate the changelog so please use a short and descriptive text with types or filenames enclosed in backticks.
If your pull request is related to an issue, please mention the related issue with its number in the PR description (not in the title), for example "Fixes #123".

Before submitting a pull request:

* Add new tests that exercise the code you have added or modified
* Run the build and tests locally with `./mvnw clean package`
* If possible run integration tests related to the part you modify (see related documentation below)
* Any code needs to be carefully reviewed by a human, especially when generated by a coding agent

## Commit message

A commit message should include a short title (if possible less than 50 characters) starting with an uppercase verb.
The title should *not* include prefixes like `fix:`, `feat:` or `docs:` or the issue/PR number.

- ✅ Add Contribution Guidelines
- ❌ GH-123: Add Contribution Guidelines
- ❌ docs: Add Contribution Guidelines
- ❌ Add Contribution Guidelines (#123)

The commit description should be wrapped at approximately 72 characters.

Commit messages should allow discoverability of related issues and PRs [by linking them](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue#linking-a-pull-request-to-an-issue-using-a-keyword) after the description with for example `Closes #123` if the issue number is 123.
That allows bi-directional navigation from the commit to the issue/PR, but also in the other way around as related mentions are added by GitHub.

All commits must include a __Signed-off-by__ trailer at the end of each commit message to indicate that the contributor agrees to the Developer Certificate of Origin.

For additional details, please refer to the blog post [Hello DCO, Goodbye CLA: Simplifying Contributions to Spring](https://spring.io/blog/2025/01/06/hello-dco-goodbye-cla-simplifying-contributions-to-spring) that Bad Monkey is aligning to. 

Please find below the example of a typical commit message:

```text
    Add Contribution Guidelines

    This commit adds CONTRIBUTING.md describing the Contribution
    procedure, mentions Contribution Guidelines in the README.md and
    mentions CODE_OF_CONDUCT in the README.md.

    Fixes #123

    Signed-off-by: Firstname Lastname <username@users.noreply.github.com>
```

If you want to only reference some issue or PR without closing it, you can use `See #123`.
Annotations should be enclosed in backticks to avoid mentioning potential related GitHub users.  

If the commit has both an issue and a PR associated, the Agent Spaces committer merging the PR should reference both the issue and the PR and ensure the title does not contain the number of the PR, for example with an issue #123 and a PR #456:
```text
    Add Contribution Guidelines

    ...

    Fixes #123
    Closes #456

    Signed-off-by: Firstname Lastname <username@users.noreply.github.com>
```

## Source code style


AgentSpaces follows the same source code style found in Spring AI, Embabel, and similar projects. 

You can find more information on these in the checkstyle guidelines used by the [core Spring Framework project](https://github.com/spring-projects/spring-framework/wiki/Code-Style) with some exceptions.
See also related [IntelliJ IDEA Editor Settings](https://github.com/spring-projects/spring-framework/blob/main/src/idea/spring-framework.xml).

The code is formatted using the [java-format plugin](https://github.com/spring-io/spring-javaformat) as part of the build.
Correct formatting will be enforced by CI.



## Wire-format changes

Wire-format changes introduce compatibility/interop, so must be considered carefully. Needs for this should be discussed in a ticket, and signed off in the ticket prior to the PR. 

The wire format is cross-language using CBOR: the Python and TypeScript clients under
`clients/` must reproduce every structure byte-identically, pinned by the
golden vectors (`agentspaces-spec/golden.json` at the workspace root, vendored at `tools/golden/golden.json`). Any change to a signed
structure, an identifier derivation, or canonical CBOR therefore requires, in
one PR: the spec update, the Java change, both client changes, and regenerated
golden vectors (`tools/golden`; the compile-and-run command is in
`docs/BUILD-ENVIRONMENTS.md`, "Regenerating the golden vectors"). CI runs the
conformance suites; the trilingual demo (`clients/run-trilingual-demo.sh`) is
the live smoke test.


## What to work on

Issues labeled `good first issue` and `help wanted` are curated entry points.
The honest gap list in `agentspaces-spec/TECH-SPEC.md` §11 (where the implementation trails
the design) is the standing roadmap; picking an item from it and discussing the
approach in an issue first is a great way to contribute.
